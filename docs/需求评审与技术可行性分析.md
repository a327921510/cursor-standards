# Cursor Standards 需求评审与技术可行性分析

> 评审对象：《Cursor Standards：需求文档与技术路线 v0.1（2026-07-03）》
> 评审目标：核验需求方案是否**闭环可实现**、技术路线是否**可行**，并给出**补充与更优方案**。
> 评审方法：对照 Cursor 官方机制（Rules / Skills / Hooks）逐条核验事实，识别闭环缺口与实现风险，给出可落地的修订建议。

---

## 0. 总体结论（TL;DR）

| 维度 | 结论 | 说明 |
|------|------|------|
| 技术可行性 | ✅ **可行** | Rules / Skills / Hooks 三大依赖机制均为 Cursor 官方支持，方案不依赖任何未公开能力 |
| 需求闭环性 | ⚠️ **基本闭环，但有若干边界未定义** | 主要缺口集中在：CLI 自身分发、版本单一真源、清理式同步（删除文件传播）、本地改动检测、hooks.json 合并、离线/异常态处理 |
| 技术路线 | ✅ **合理**，建议微调 | Bash MVP → Go 二进制的演进正确；建议把「版本获取用 `git ls-remote --tags`」「clean sync」「integrity manifest」提前到 MVP |
| 更优方案 | 见 §5 | 建议引入**「全局基线 + 项目 pin」的混合分发**、复用 **skills.sh 生态**、以及对升级提醒机制的**降级兜底** |

一句话：**方案闭环可实现，路线可行**；但当前文档偏「happy path」，需要补齐约 8 处工程边界，并对「升级提醒」这一核心卖点做**可靠性降级设计**（见 §3.3）。

## 1. 事实核验：三大依赖机制是否成立

方案的可行性完全取决于三个 Cursor 机制。逐一核验（基于 Cursor 官方文档，2026-07）：

### 1.1 Rules（`.cursor/rules/*.mdc`）✅ 成立，但有 2.0 行为变更

- 位置与格式正确：Rules 位于 `.cursor/rules/`，必须是 `.mdc` 扩展名（`.md` 会被 Rules 系统忽略），frontmatter 字段 `description` / `globs` / `alwaysApply` 与文档一致。来源：[Cursor Docs – Rules](https://cursor.com/docs/rules)。
- **可放入子目录**：Cursor 会递归读取 `.cursor/rules/` 下的子目录，因此把中央规范放到 `.cursor/rules/standards/` 是可行的，与项目本地 `.cursor/rules/local.mdc` 天然隔离。✅ 这直接支撑了 R-01 与「分层共存」。
- ⚠️ **重要行为变更（Cursor 2.0）**：`alwaysApply:false` + `globs` 的规则**不再因「打开文件」而自动加载**，只有当匹配文件被 `@` 引用或被 Agent 读取/编辑时才 auto-attach。来源：[Cursor 社区反馈帖](https://forum.cursor.com/t/cursor-2-0-project-rule-mdc-files-with-glob-patterns-not-auto-loaded-in-conversations/140641)。
  - **影响**：文档 R-04 用 `globs` 限定 `python.mdc`/`typescript.mdc` 的作用范围是**正确设计**，但「进入 Python 项目就自动生效」的心智模型不成立——它是「碰到 `.py` 文件时才注入」。
  - **结论**：`general.mdc` / `git-workflow.mdc` 用 `alwaysApply:true`（R-05）是对的；语言规则保持 glob-scoped 也是对的；只需在文档里**校正期望**（见 §4-J）。

### 1.2 Skills（`.cursor/skills/**/SKILL.md`）✅ 成立

- Cursor 原生支持 Skills，自动扫描 `.cursor/skills/`、`.agents/skills/` 及全局 `~/.cursor/skills/`；每个 skill 是一个含 `SKILL.md` 的文件夹，且**递归读取子目录**。来源：[Cursor Docs – Agent Skills](https://cursor.com/docs/skills)。
- 因此 `install` 产出的 `.cursor/skills/standards/<skill>/SKILL.md` 布局**成立**。SKILL.md frontmatter 关键字段为 `name`（须与文件夹名一致、仅小写/数字/连字符）与 `description`（触发词，支撑 R-06），可选 `paths`（glob 作用域）。
- ⚠️ **存在成熟的同类生态**：官方与社区已有 `npx skills` / [skills.sh](https://skills.sh/) CLI 用于安装/管理 skills；Cursor 也兼容 `.claude/skills/`、`.codex/skills/`。这意味着**「skills 分发」这一半轮子已有现成工具**，本方案可选择复用或至少在文档中说明差异（见 §5.3）。

### 1.3 Hooks（`.cursor/hooks.json` + `sessionStart`）✅ 成立，但有关键限制

- `hooks.json` 位置正确：项目 `.cursor/hooks.json`、用户 `~/.cursor/hooks.json`、企业 `/etc/cursor/hooks.json`。`sessionStart` 事件存在。来源：[Cursor Docs – Hooks](https://cursor.com/docs/hooks)。
- **`sessionStart` 的官方输出契约支持注入上下文**：
  ```json
  { "env": { "KEY": "VALUE" }, "additional_context": "<注入到会话初始 system context 的文本>" }
  ```
  这正好用于 V-04「有升级时注入提示」。且该 hook 为 **fire-and-forget（不阻塞 agent loop）**，天然满足 V-04「不阻断」。✅
- ⚠️ **三个必须写进风险表的限制**：
  1. **云端 Agent 不触发 `sessionStart`**：官方明确 Cloud Agent（cursor.com/agents）没有 `sessionStart`/`beforeSubmitPrompt` 触发点。→ 升级提醒只在**本地 IDE** 生效，云端需靠 CI（V-05）兜底。
  2. **注入可靠性有已知缺陷**：社区报告 `sessionStart` / `postToolUse` 的 `additional_context` 存在「hook 触发、JSON 合法、但注入内容被静默丢弃」的情况。→ 不能把升级提醒**唯一**依赖 hook 注入。
  3. **Hooks 仍是 beta，且需用户在设置中启用**；`beforeSubmitPrompt` 无法修改 prompt 文本。
- **供应链风险（重要）**：`check-standards.sh` 由 hook 在每次会话开始**自动执行**。谁能改中央仓库，谁就能在所有开发者机器上于 session start 时执行代码。这是比 NF-05（不执行远程脚本）更隐蔽的信任升级点，需在风险表升级处理（见 §4-N）。

> **核验小结**：三大机制全部成立，文档对机制的引用准确度高。真正需要补强的是 **Cursor 2.0 的 glob 行为**、**sessionStart 的云端缺失与注入不可靠**、以及 **hook 的供应链信任**这三处「机制细节」。

## 2. 需求内部一致性 / 闭环性检查

对照文档 §3–§5 的自洽性，发现以下**闭环缺口**（未定义即无法实现的边界）：

| # | 缺口 | 位置 | 为何是闭环问题 |
|---|------|------|----------------|
| G1 | **CLI 自身如何分发到各电脑 / 上 PATH** 未定义 | §3.2 / §9 | 方案要解决「换电脑不一致」，但 `bin/cursor-std` 本身的安装（PATH/symlink/bootstrap 脚本）在 MVP 未定义。存在先有鸡还是先有蛋：必须先拿到 CLI 才能 install。 |
| G2 | **版本单一真源未定死**：`VERSION` 文件与 git tag 二选一（R-02） | §3.1 | 两者会 drift。若 `check` 比 tag 而 lock 写 VERSION，可能永远「有升级」或永远「最新」。需规定 tag 为准 + CI 断言 `VERSION == tag`。 |
| G3 | **删除/重命名的规则文件如何传播** 未定义 | §3.2 install 产出 | 若 install 只是「复制覆盖」，中央仓库删掉一个 rule 后，项目侧 `standards/` 会残留孤儿文件，违反 NF-03 幂等与「结果一致」。需 clean sync（先清空 `standards/` 子树再落地）。 |
| G4 | **本地对 `standards/` 的手改如何检测** 未定义 | §6 风险表仅「README 提醒」 | 风险表说「install 前 diff 警告」，但没有实现载体（无 checksum/manifest 就无法 diff）。需 lock 内存 manifest 校验和。 |
| G5 | **`init` 写入 hooks.json 的合并语义** 未定义 | §3.2 C-04 | 项目若已有 `.cursor/hooks.json`（例如已有 `beforeShellExecution` 审计），`init` 直接写会覆盖。需「合并」，但合并 JSON 需要 jq → 与 NF-01 零依赖冲突，需明确取舍。 |
| G6 | **离线 / 异常态**：从 `STANDARDS_HOME`（本地 clone，可能在分支/detached/无 tag/dirty）安装时，lock 的 `version`/`commit` 取值规则未定义 | §3.1 NF-04 | 无 tag 时 `version` 写什么？dirty 时如何标记？否则 lock 不可信。 |
| G7 | **成功指标「drift < 20%」的度量机制** 缺失 | §7 | 非目标里明确「不做 Web Dashboard」，但没有集中遥测就无法度量全公司 drift。度量口径与非目标冲突，需改为「CI 聚合」或删指标。 |
| G8 | **冲突优先级表述与 Cursor 实际不符** | §3.4 | 文档称「Team > Project(含 standards) > User Rules」的**覆盖**优先级。实际上 Cursor 会把各来源规则**一并**提供给 Agent，并不存在硬性「抑制某来源」的覆盖机制。冲突应靠**设计（作用域/命名）规避**，不能依赖优先级自动消解。 |

> 结论：**主体闭环**（安装→锁定→检查→升级 的数据流是完整的），但上表 8 项属于「不定义就写不出正确实现」的硬边界，需在 Phase 0/1 补齐 schema 与行为约定。

## 3. 逐能力可行性评估

### 3.1 `install` / `update`（C-01/C-03）✅ 可行

- copy 模式是正确的默认（symlink 在 Windows/Git Bash 需开发者模式或管理员权限，坑多）。
- **必须补**：clean sync（G3）。建议实现语义为「原子替换 `standards/` 子树」：
  ```bash
  # 伪代码：只接管 standards/ 子目录，绝不碰同级的 local.mdc
  tmp="$(mktemp -d)"
  cp -R "$SRC/rules/."   "$tmp/rules-standards/"
  rm -rf "$DEST/.cursor/rules/standards"
  mkdir -p "$DEST/.cursor/rules"
  mv "$tmp/rules-standards" "$DEST/.cursor/rules/standards"
  ```
  这样既满足幂等（NF-03），又传播删除，又不破坏 `local.mdc`（Phase 1 验收项）。
- **必须补**：写 lock 前生成 `standards/` 文件的 checksum manifest（G4），供下次 install/update 前检测手改并告警。

### 3.2 `check`（C-02 / V-01）✅ 可行，建议改用纯 git

- **建议主实现用 `git ls-remote --tags`**，而非 GitHub/GitLab API：
  - 零额外依赖（NF-01 只需 git，不必 curl），跨 GitHub/GitLab/自建/Gitea 通用（免去 Phase 3「私有 API token」的大部分工作），也天然支持 SSH 私有仓库。
  ```bash
  latest="$(git ls-remote --tags --refs "$SOURCE" \
            | awk -F/ '{print $NF}' | sort -V | tail -n1)"
  ```
- ⚠️ **`sort -V` 的可移植性**：GNU coreutils 支持；macOS 近版 BSD `sort` 亦支持 `-V`，但**旧 macOS / 某些 Git Bash 环境不保证**。建议**内置一个纯 bash 的 semver 比较函数**，避免依赖 `sort -V`（提升 NF-01 成功率）。
- 离线态（NF-04）：`check` 退化为「对比本地 `STANDARDS_HOME` 的 `git describe --tags` 与 lock」，文档已提及，✅。
- 退出码语义（V-05）清晰：有升级返回 1，供 CI 用。✅

### 3.3 升级提醒（V-04）⚠️ 可行但需降级设计 —— 这是全案最脆弱的一环

「打开 Agent 即感知升级」是方案的核心卖点，但依赖链最弱（见 §1.3）。建议**三层降级**，保证「至少有一层可靠」：

1. **主路径**：`sessionStart` hook 返回 `additional_context`（本地 IDE，注入成功时体验最好）。
2. **兜底 1（可靠）**：hook 同时把结果**写入文件**（如 `.cursor/.standards-check`）并**打印到 stderr / 终端**；即使 `additional_context` 被静默丢弃，开发者仍能从终端看到。
3. **兜底 2（云端/CI）**：`cursor-std check` 在 CI 中以退出码 1 告警（V-05），覆盖云端 Agent 无 `sessionStart` 的场景。

另外：
- **性能**：sessionStart 每次会话都跑网络会拖慢体验。建议 hook **缓存**远程 tag 结果（如 `~/.cache/cursor-std/<repo-hash>.json`，TTL 若干小时），仅当结果变化才提示；`git ls-remote` 也应设超时。
- **降噪**：仅在「有新版本」时注入，无更新时静默。

### 3.4 `init`（C-04）⚠️ 需定义合并语义（G5）

- 若坚持零依赖：`init` 检测到已存在 `hooks.json` 时**不覆盖**，改为打印「请手动把以下片段合并进 hooks.json」并写一个 `.cursor/hooks.standards.json` 供参考。
- 若允许可选依赖：检测到 `jq` 时自动合并，否则降级为上面的手动提示。建议后者（渐进增强）。

### 3.5 `version` / `diff`（C-05/C-06）✅ 可行，低风险

- `diff` 展示 lock→latest 的 CHANGELOG 摘要：可用 `git log <lockCommit>..<latestTag> -- CHANGELOG.md` 或直接截取 CHANGELOG 版本段落，实现简单。

### 3.6 版本 pin（V-02/V-03）✅ 可行

- `--version` → `git fetch --tags` 后 checkout 该 tag 的树；`--commit` → checkout 该 commit。lock 记录 `version`+`commit` 已足够复现。建议 MVP 就把 `--version` 做了（成本低、对「生产分支锁定」价值高），可从 Phase 3 提前。

## 4. 补充建议（按优先级）

- **[P0] G1 CLI 自举**：提供 `install.sh`（`curl` 之外的方式）：clone 仓库后运行 `./install.sh`，将 `bin/cursor-std` symlink 到 `~/.local/bin` 或提示加入 PATH；文档给出「一次性 bootstrap」步骤。跨机器一致性靠「clone 同一仓库 + 固定 PATH」达成。
- **[P0] G2 版本真源**：规定 **git tag 为唯一真源**，`VERSION` 文件为镜像；发版 CI 断言 `VERSION == 最新 tag`，否则 fail。
- **[P0] G3 clean sync + [P0] G4 integrity manifest**：见 §3.1，直接进 MVP 验收项。
- **[P0] §1.3 供应链**（见 §4-N 下条）：把 hook 自动执行的信任风险写进风险表。
- **[P1] G8 优先级表述纠正**：把「Team > Project > User 的覆盖」改述为「多来源规则并存注入；冲突靠作用域/命名规避，不依赖优先级消解」。
- **[P1] §4-J glob 期望校正**：文档说明「语言规则是 auto-attach（碰到匹配文件才注入），非全程常驻」。
- **[P1] 可测试性**：MVP 就引入 `shellcheck` 静态检查 + `bats-core` 用例 + CI 矩阵（ubuntu-latest / macos-latest / windows(git-bash)）。所有脚本 `set -euo pipefail`、`IFS` 安全。这是当前文档**完全缺失**的一块（无测试策略）。
- **[P1] 可移植性清单**：避免 GNU-only 用法（`realpath`、`mktemp` 参数、`sort -V`、`sed -i` 的 BSD 差异、`readlink -f`），或封装 compat 函数。
- **[P2] G6 异常态 schema**：定义无 tag → `version:"0.0.0+<shortsha>"`、dirty → lock 增 `"dirty":true` 字段并告警。
- **[P2] G7 指标度量**：把「drift < 20%」改为「通过各仓库 CI 上报 lock 版本到一个汇总 job / badge」，或降级为定性指标，与「不做 Dashboard」的非目标对齐。
- **[N 供应链缓解]**：CODEOWNERS + 分支保护 + **签名 tag（`git tag -s`）**；hook 脚本保持**极简、可 review、只读检查**；文档强调「hook 属于选装、需用户显式启用」；生产分支用 `--commit` pin。

### lock 文件建议增补字段

```json
{
  "source": "git@github.com:org/cursor-standards.git",
  "version": "1.2.0",
  "commit": "abc123def456",
  "installedAt": "2026-07-03T09:00:00+08:00",
  "installMode": "copy",
  "cliVersion": "1.2.0",            // 便于排查是哪个 CLI 版本写的
  "dirty": false,                    // 从本地 clone 安装时源是否有未提交改动
  "manifest": {                      // standards/ 各文件校验和，供手改检测(G4)
    "rules/standards/general.mdc": "sha256:...",
    "skills/standards/commit-helper/SKILL.md": "sha256:..."
  }
}
```

## 5. 是否有「更优方案」

### 5.1 混合分发：全局基线 + 项目 pin（推荐纳入路线）

Cursor 支持**用户级** `~/.cursor/rules/` 与 `~/.cursor/skills/`（全局，跨项目、跨仓库自动生效）。因此可提供两种叠加模式：

- **全局基线**：`cursor-std install --global` 安装到 `~/.cursor/`，一台机器装一次，所有项目自动获得团队通用规范——**天然解决「换电脑/跨项目一致」**，无需每个项目复制。
- **项目 pin**：需要版本锁定（生产分支、审计）的仓库，再在项目内 `install` 并写 lock。

> 取舍：全局模式无法按项目 pin 版本，适合「通用软规范」；项目模式可锁版本，适合「强合规仓库」。二者叠加即 §3.4 的分层。建议至少在文档中给出这一选项，很多团队会更偏好「全局一次装」。

### 5.2 分发机制备选对比（供 Phase 3 决策）

| 方案 | 版本 pin | 删除传播 | 跨语言 | 复杂度 | 备注 |
|------|---------|---------|--------|--------|------|
| **CLI + copy（本案 MVP）** | 手动 lock | 需 clean sync | ✅ | 低 | 推荐 MVP |
| git **submodule** 指到 `.cursor/rules/standards` | ✅ 原生 | ✅ 原生 | ✅ | 中 | 但 submodule 会把 `bin/lib` 也拉进来，需**内容专用仓库/分支**；submodule UX 较劝退 |
| git **subtree** | ✅ | ✅ | ✅ | 中高 | 命令复杂，不建议作为默认 |
| **skills.sh / `npx skills`** | 生态自带 | 生态自带 | ✅ | 低 | **仅覆盖 skills 半边**；rules 仍需本案 |

结论：**CLI + copy 作为 MVP 是正确选择**；submodule 仅作为「强 pin」可选项（文档 Phase 3 已列，保留即可）。

### 5.3 复用 skills.sh 生态

由于 `.cursor/skills/` 已有成熟 CLI（`npx skills` / skills.sh），可考虑：`cursor-std` 只专注 **rules 分发 + 版本锁 + 升级提醒**，skills 部分**可选桥接** skills.sh（在有 node 的环境）或仍用自带 copy。这能减少重复造轮子，也避免与生态标准分裂。**但需权衡** NF-01 零依赖——桥接应为可选增强，不作硬依赖。

### 5.4 与企业版 Team Rules 的关系

若团队已在 Cursor Business/Enterprise，**Team Rules + Enterprise Hooks 分发**本身就能集中下发规范与 hooks。本案定位为「不依赖企业版的通用方案」是合理的差异化；文档非目标已说明并行，✅ 保留。

## 6. 对技术路线（§5）的修订建议

整体阶段划分正确。建议做如下「前移 / 补充」：

- **Phase 0 补**：定死 lock schema（含 manifest/dirty 字段）、版本真源=tag、clean sync 语义、hooks 合并策略、可移植性与测试基线（shellcheck + bats）。这些是「不定义就返工」的项。
- **Phase 1（MVP）前移**：`git ls-remote --tags` 版本检查、clean sync、integrity manifest、`--version` pin、升级提醒三层降级（§3.3）。MVP 验收增补：
  - [ ] 中央仓库**删除**一个 rule 后，项目 `update` 能移除对应孤儿文件（clean sync）
  - [ ] 手改 `standards/` 后再 `install` 会**告警**（manifest 校验）
  - [ ] 已有 `hooks.json` 的项目 `init` 不被覆盖（合并/提示）
  - [ ] `sort -V` 不可用的环境下 semver 比较仍正确（纯 bash compare）
  - [ ] CI（云端无 sessionStart）下 `check` 以退出码 1 提示升级
- **Phase 2 补**：把「供应链保护（签名 tag / CODEOWNERS / 分支保护）」作为团队推广前置项；CI 示例补 warn-only 与 fail 两种模式。
- **Phase 3 保留**：Go 单文件二进制（彻底解决 Windows 与可移植性）、submodule 强 pin、私有 API（若不用 `git ls-remote` 兜底再考虑）。

---

## 7. 风险表增补（补入原 §6）

| 风险 | 影响 | 对策 |
|------|------|------|
| **hook 供应链**：中央仓库被改即在所有开发者机器 session start 执行代码 | 高（远程代码执行面） | 签名 tag + CODEOWNERS + 分支保护；hook 脚本极简只读；hook 选装 + 用户显式启用；生产分支 `--commit` pin |
| `sessionStart` 注入被静默丢弃 / 云端不触发 | 升级提醒失效 | 三层降级（文件+stderr+CI 退出码），不把提醒唯一寄托于 hook 注入 |
| GNU-only 命令在 macOS/Git Bash 行为不同 | install 在部分环境失败 | 封装 compat 函数；CI 三平台矩阵；避免 `sort -V`/`readlink -f`/`sed -i` 差异 |
| clean sync 误删同级 `local.mdc` | 破坏项目本地规则 | 严格只接管 `standards/` 子目录，测试覆盖 |
| VERSION 与 tag drift | check 结果不可信 | tag 为真源，发版 CI 断言相等 |

---

## 8. 结论

1. **技术可行**：Rules / Skills / Hooks 均为 Cursor 官方支持，方案不依赖未公开能力；对机制的引用整体准确。
2. **需求基本闭环**：核心数据流（install→lock→check→update）完整；但需补齐 §2 列出的 8 处工程边界（尤以 CLI 自举、版本真源、clean sync、integrity manifest、升级提醒降级 为 P0）。
3. **路线可行**：Bash MVP → Go 二进制的演进正确；建议把 `git ls-remote` 版本检查、clean sync、manifest、`--version` pin 前移至 MVP。
4. **更优补充**：引入「全局基线 + 项目 pin」混合分发、复用 skills.sh 生态（可选桥接）、并对「升级提醒」这一最脆弱环节做三层降级与缓存降噪。

> 按上述补齐后，方案即可从「happy-path 可用」升级为「工程闭环、跨平台稳健、可长期演进」的正式 v1.0 规范。

## 附录 A：能否用 `npx skills` 承载定制化的 skills / rules 分发？

结论先行：

| 目标 | 能否用 `npx skills` 实现 | 说明 |
|------|--------------------------|------|
| **Skills 分发/更新** | ✅ **基本可以**（有明显取舍） | `npx skills` 就是干这个的包管理器 |
| **Rules（`.mdc`）分发** | ❌ **不能** | 该 CLI 只管 `SKILL.md`，完全不碰 `.cursor/rules/*.mdc` |
| **你要的「语义化版本 / tag / commit pin」** | ❌ **原生不支持** | 无 `@version`/`@commit` git-ref pin；`update` 拉的是分支 HEAD |
| **零运行时依赖（NF-01）** | ❌ 冲突 | 需要 Node/npx runtime |

因此**它不能作为「rules + skills 统一、可版本追溯」的单一分发底座**，但**可作为 skills 那一半的可选安装器 / 互操作层**。下面展开。

### A.1 `npx skills` 是什么、能做什么

Vercel Labs 出的开源 CLI（配套 [skills.sh](https://skills.sh/) 排行榜与 [agentskills.io](https://agentskills.io/) 开放标准），是「agent skills 的包管理器」。核心能力（来源：[vercel-labs/skills](https://github.com/vercel-labs/skills/)、[skills 文档](https://vercel-labs-skills.mintlify.app/)）：

- **来源灵活**：`owner/repo` 简写、完整 GitHub/GitLab URL、`owner/repo@skill-name`（选 skill）、子目录路径、任意 git URL、本地路径。→ **可以指向你自己的 `cursor-standards` 私有仓库**（私有仓库靠 `GITHUB_TOKEN`）。
- **命令**：`add` / `find` / `list` / `check` / `update [skills…]` / `remove` / `init`（脚手架新 skill）/ `use` / `experimental_install`（按 lockfile 复现）。
- **作用域**：`-g` 全局装到 `~/.cursor/skills/`、`~/.agents/skills/`；不带则装项目级 `.agents/skills/`。`-a cursor|claude-code|codex` 指定 agent。
- **安装方式**：默认 symlink，`--copy` 可选。
- **更新机制**：读 `~/.agents/.skill-lock.json`，把本地 skill 文件夹 hash 与 GitHub 上**默认分支（main）**的版本比对；**仅追踪 `-g` 全局安装**，项目级不进 `update`。

### A.2 与你的需求逐条对齐（关键取舍）

| 你的需求 | `npx skills` 支持度 | 差距说明 |
|----------|--------------------|----------|
| Rules（`.mdc`）分发（R-01/R-04/R-05） | ❌ | CLI 完全不处理 rules，只处理 SKILL.md |
| Skills 分发（R-01/R-06） | ✅ | `add`/`update`/`find` 齐全 |
| 自建/私有仓库源 | ✅ | git URL + `GITHUB_TOKEN` |
| 全局安装、跨项目（解决换机） | ✅ | `-g` → `~/.cursor/skills/` |
| 项目级安装 + 项目锁 | ⚠️ | 能装，但 `update` 不追踪项目级；且它用自己的 `skills-lock.json`，非你的 `.standards-lock.json` |
| semver / tag pin（V-02） | ❌ | 无 `@version` git-ref；`@` 只是选 skill 名 |
| commit pin（V-03） | ❌ | 同上 |
| 基于 git tag 的升级检测（V-01） | ❌ | 它比对的是**分支 HEAD 的文件夹 hash**，不认你的 `v1.2.0` tag |
| 可复现锁定 | ⚠️ | 靠提交 `skills-lock.json` + `experimental_install`，语义是「锁文件内容」而非「锁 tag/commit」 |
| CI 退出码提醒（V-05） | ⚠️ | `check` 存在，但语义是「hash 变了」，不是「落后于某个发布版本」 |
| 零依赖（NF-01） | ❌ | 需 Node/npx |

**最要命的两点**：
1. **rules 管不了**——而你的核心团队规范（`general.mdc`、`git-workflow.mdc` 这类 `alwaysApply:true`）恰恰是 rules。
2. **没有真正的版本 pin / tag 语义**——你方案的卖点「版本可追溯、可 pin、按 tag 升级提醒」正好是它的短板。它的模型是「跟随分支 HEAD 滚动更新」。

> 补充：`alwaysApply:true` 或带 `globs` 的 rule **不适合转成 skill**。Cursor 2.4+ 的 `/migrate-to-skills` 也**明确拒绝迁移**这两类 rule（因为 skill 是「按需/渐进加载」，而它们要「常驻/按文件触发」）。所以「把 rules 全改写成 skills 来蹭 `npx skills`」这条路，会**丢掉你最重要的常驻规范语义**，不可取。

### A.3 推荐：混合 / 互操作，而非替换

不建议用 `npx skills` 做统一底座；建议**各取所长**：

- **Rules（`.mdc`）**：始终由你自己的 `cursor-std`（copy + `.standards-lock.json` + clean sync + manifest）分发与版本管理。这是 `npx skills` 覆盖不到、且你最需要治理的部分。
- **Skills**：两种可选姿势——
  - **姿势 1（推荐，低耦合）**：skills 也由 `cursor-std` 一并 copy + 纳入同一个 `.standards-lock.json`，实现「rules 与 skills 同版本、同 tag、同 pin」的**统一治理**。同时把 skills 目录写成**符合开放标准**（`.agents/skills/` 或 `.cursor/skills/`），这样任何人**也能**用 `npx skills add <你的仓库>` 临时全局安装——即「治理走自己的 CLI，生态兼容白送」。
  - **姿势 2（可选增强桥接）**：在检测到 Node 时，`cursor-std install` 内部对 skills 部分调用 `npx skills add <repo> -a cursor --copy -y`；无 Node 时回退到自带 copy。**注意**：这会引入 Node 软依赖，且 skills 与 rules 的 lock/版本语义割裂（两套锁），治理一致性下降，仅在你确实想吃到 skills.sh 的发现/排行榜生态时才值得。

**决策建议**：优先**姿势 1**。即——**自建 CLI 统一治理 rules+skills 的版本与 pin；目录遵循开放标准，从而与 `npx skills` 生态天然互操作**。把 `npx skills` 当作「面向个人的可选安装/发现入口」，而不是团队规范的分发底座。

### A.4 若坚持以 `npx skills` 为主，需要接受的改动

- 放弃「统一 lock + semver/commit pin」，改用 skills.sh 的 `skills-lock.json` + `experimental_install` 复现模型，并接受「跟随分支滚动」的升级语义（用发布分支而非 tag 做版本闸门）。
- rules 仍需另建分发通道（copy/submodule），即**无论如何都省不掉自己的一半机制**。
- 接受 Node/npx 运行时依赖，NF-01「零依赖」需相应改写。
