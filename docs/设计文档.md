# 第一部分：需求文档与技术路线（原始 v0.1）

> 说明：以下为立项时的原始需求，**保留原样**作为背景。其中若干条目在评审后有调整（如规则命名加 `std-` 前缀、冲突优先级表述纠正、`diff` 不实现等），以第二/三/四部分为准。

> 方案：**独立 Git 仓库 + 通用 CLI**
> 目标：跨项目、跨语言、跨电脑，统一分发 Cursor Rules 与 Skills，并支持版本管理与升级提醒。

## 1. 项目背景

### 1.1 现状与痛点

| 痛点 | 说明 |
|------|------|
| 规则分散 | User Rules、项目 `.cursor/rules/`、个人习惯混用，难以统一 |
| 无法版本化 | User Rules 无 semver，团队规范变更无法 review |
| 语言绑定 | 若用 npm/pip 包分发，Python 项目需装 Node，反之亦然 |
| 跨电脑不一致 | 换机器后规则缺失，需手动复制 |
| 升级无感知 | 中央规范更新后，各项目开发者不知道要同步 |

### 1.2 目标

建立一套 **与项目语言无关** 的 Cursor 规范分发体系：

1. **单一来源**：所有 Rules / Skills 维护在一个独立 Git 仓库
2. **通用安装**：任意项目（Python / Node / Go / 混合 monorepo）通过 CLI 一键同步
3. **版本可追溯**：每次安装写入 lock 文件，支持 semver 或 commit pin
4. **升级可提醒**：打开 Cursor Agent 或执行 check 命令时，检测是否有新版本
5. **分层共存**：与 User Rules、项目本地 Rules 兼容，冲突按 Cursor 优先级处理

### 1.3 非目标（第一版不做）

- 不做 Cursor 插件 / Marketplace 发布
- 不做 Web Dashboard 管理界面
- 不替代 Cursor Team Rules（企业版可并行使用）
- 不自动静默升级（需开发者确认或 CI 触发）

## 2. 用户与使用场景

| 角色 | 场景 |
|------|------|
| **规范维护者** | 在 `cursor-standards` 仓库修改 rules/skills，打 tag，发 CHANGELOG |
| **项目开发者** | clone 业务项目 → 运行 `cursor-std install` → 开始用 Cursor Agent |
| **Tech Lead** | 在 CI 中检查 lock 版本是否与要求一致 |
| **个人开发者** | 可选：dotfiles 同步 `~/.cursor/`，与项目规范叠加 |

## 3. 功能需求

### 3.1 中央仓库（cursor-standards）

| 编号 | 需求 | 优先级 |
|------|------|--------|
| R-01 | 仓库包含 `rules/`（`.mdc`）与 `skills/`（`SKILL.md`） | P0 |
| R-02 | 根目录 `VERSION` 文件或 git tag 作为版本号（semver） | P0 |
| R-03 | `CHANGELOG.md` 记录每次版本变更 | P1 |
| R-04 | Rules 按语言/域拆分，使用 `globs` 限定作用范围 | P0 |
| R-05 | 提供 `general.mdc`（`alwaysApply: true`）作为全项目通用规范 | P0 |
| R-06 | Skills 的 `description` 含触发词，便于 Agent 自动选用 | P1 |

### 3.2 通用 CLI（cursor-std）

CLI 实现语言：**Bash（MVP）**，零依赖，macOS / Linux / Windows(Git Bash) 可用；后期可选 Go 单文件二进制。

| 编号 | 命令 | 行为 | 优先级 |
|------|------|------|--------|
| C-01 | `cursor-std install [目标目录]` | 将 rules/skills 同步到 `<目标>/.cursor/` | P0 |
| C-02 | `cursor-std check [目标目录]` | 对比 lock 与远程最新版本，输出是否需要升级 | P0 |
| C-03 | `cursor-std update [目标目录]` | 拉取最新规范并重新 install | P0 |
| C-04 | `cursor-std init [目标目录]` | 首次接入：install + 写入 hooks + 生成项目 wrapper 脚本 | P1 |
| C-05 | `cursor-std version` | 输出 CLI 与 standards 仓库版本 | P1 |
| C-06 | `cursor-std diff [目标目录]` | 展示 lock 版本与 latest 之间的 CHANGELOG 摘要 | P2 |

**install 策略（可配置）**：`copy`（复制到 `.cursor/rules/standards/`，默认）/ `symlink`（可选）。

**lock 文件格式**（原始设想）：

```json
{
  "source": "git@github.com:org/cursor-standards.git",
  "version": "1.2.0",
  "commit": "abc123def456",
  "installedAt": "2026-07-03T09:00:00+08:00",
  "installMode": "copy"
}
```

### 3.3 版本检查与升级提醒

| 编号 | 需求 | 优先级 |
|------|------|--------|
| V-01 | `check` 通过 git tag 或 GitHub/GitLab API 获取 latest version | P0 |
| V-02 | 支持 pin 到指定版本：`cursor-std install --version 1.2.0` | P1 |
| V-03 | 支持 pin 到 commit：`cursor-std install --commit abc123` | P2 |
| V-04 | Cursor `sessionStart` Hook 调用 check，有升级时注入提示（不阻断） | P1 |
| V-05 | 退出码：`check` 有升级返回 1，供 CI 使用 | P1 |

### 3.4 与 Cursor 其他机制的关系

| 机制 | 关系 |
|------|------|
| User Rules | 互补：User Rules 放个人偏好；standards 放团队规范 |
| Project Rules（本地） | 可叠加：项目 `.cursor/rules/local-*.mdc` 覆盖 standards |
| Team Rules | 并行：Team Rules 优先级更高 |

> ⚠️ 原始文档给出的「Team > Project > User」覆盖优先级在评审中被纠正，见第二部分 §2-G8。

### 3.5 非功能需求

| 编号 | 需求 | 指标 |
|------|------|------|
| NF-01 | 零运行时依赖（MVP 仅需 bash、git、curl 可选） | install 成功率 |
| NF-02 | install 耗时 | < 3s（本地 copy） |
| NF-03 | 幂等性 | 重复 install 结果一致 |
| NF-04 | 可离线 install | 支持 `STANDARDS_HOME` 指向本地 clone |
| NF-05 | 安全 | 不从不可信 URL 执行 remote script；文档明确推荐 clone + 本地 install |

## 4. 系统架构（原始设想）

- 中央仓库：`rules/ skills/ VERSION CHANGELOG bin/cursor-std lib/ templates/`。
- CLI：`install / check / update / init` 同步到各语言项目的 `.cursor/`。
- 目标项目：`.cursor/rules/standards`（受管）+ `.cursor/rules/local.mdc`（本地）+ `.standards-lock.json`。

## 5. 技术路线（原始设想）

```
Phase 0 设计 ──► Phase 1 MVP ──► Phase 2 团队化 ──► Phase 3 自动化
```

- **Phase 1（MVP）**：`install` / `check` / `update` + hooks 模板 + 试点。
- **Phase 2**：`init`、多语言规则、CHANGELOG/发版流程、接入指南、CI 示例。
- **Phase 3**：Go 二进制、`--version`/`--commit` pin、`diff`、submodule、私有 Git API、npm 薄封装。

**发版流程**：改 rules/skills → 更新 CHANGELOG+VERSION → PR review → merge → `git tag v1.x.x` → 各项目 check/update。

# 第二部分：技术可行性评审

> 评审目标：核验需求是否**闭环可实现**、技术路线是否**可行**，并给出补充与更优方案。
> 评审方法：对照 Cursor 官方机制（Rules / Skills / Hooks）逐条核验事实（依据 2026-07 官方文档）。

## 2-0. 总体结论

| 维度 | 结论 | 说明 |
|------|------|------|
| 技术可行性 | ✅ **可行** | Rules / Skills / Hooks 三大依赖机制均为 Cursor 官方支持，不依赖未公开能力 |
| 需求闭环性 | ⚠️ **基本闭环，有若干边界需补** | 集中在：CLI 自身分发、版本单一真源、清理式同步、本地改动检测、hooks 合并、离线/异常态 |
| 技术路线 | ✅ **合理**，建议微调 | 将 `git ls-remote --tags`、clean sync、integrity manifest、`--version` pin 前移至 MVP |
| 更优方案 | 见 §2-5 | 「全局基线 + 项目 pin」混合分发、复用 skills.sh 生态、升级提醒降级兜底 |

## 2-1. 事实核验：三大依赖机制

### Rules（`.cursor/rules/*.mdc`）✅ 成立，但有 2.0 行为变更
- 位置/格式正确；`.md` 无 frontmatter 会被忽略。可放子目录 → `.cursor/rules/standards/` 与 `local.mdc` 天然隔离。来源：[Cursor Docs – Rules](https://cursor.com/docs/rules)。
- ⚠️ **Cursor 2.0**：`alwaysApply:false` + `globs` 的规则**不再因「打开文件」自动加载**，仅当匹配文件被 `@` 引用/被 Agent 编辑时 auto-attach。→ 语言规则「碰到文件才注入」，非「进项目就常驻」；常驻规范用 `alwaysApply:true`。

### Skills（`.cursor/skills/**/SKILL.md`）✅ 成立
- Cursor 递归扫描 `.cursor/skills/`（及 `.agents/skills/`、全局 `~/.cursor/skills/`）；每个 skill 一个含 `SKILL.md` 的文件夹。来源：[Cursor Docs – Agent Skills](https://cursor.com/docs/skills)。
- 存在成熟同类生态 `npx skills` / [skills.sh](https://skills.sh/)（详见附录 A）。

### Hooks（`.cursor/hooks.json` + `sessionStart`）✅ 成立，但有关键限制
- `sessionStart` 官方支持 `{ "env": {...}, "additional_context": "..." }`，fire-and-forget（满足 V-04「不阻断」）。来源：[Cursor Docs – Hooks](https://cursor.com/docs/hooks)。
- ⚠️ 限制：**云端 Agent 不触发** `sessionStart`；社区报告 `additional_context` **注入可能被静默丢弃**；Hooks 仍 beta 需启用。
- ⚠️ **供应链风险**：hook 每次会话自动执行脚本，中央仓库控制者即可在所有开发者机器上执行代码。

## 2-2. 闭环缺口（评审时发现，均已在实现中补齐，见第四部分）

| # | 缺口 | 补齐方式 |
|---|------|----------|
| G1 | CLI 自身如何上 PATH 未定义 | `install.sh` 引导脚本 + `STANDARDS_HOME` |
| G2 | 版本真源（VERSION vs tag）会 drift | tag 为真源，`release-check` CI 断言相等 |
| G3 | 删除的规则文件如何传播 | **clean sync**：原子替换 `standards/` 子树 |
| G4 | 本地手改 `standards/` 无法检测 | lock 内 **manifest**（sha256）+ `verify` |
| G5 | `init` 写 hooks.json 的合并语义 | 不覆盖既有；写 `hooks.standards.json` + 手动合并提示 |
| G6 | 离线/异常态 lock 取值 | 无 tag→回退 VERSION/`0.0.0`；`dirty` 字段告警 |
| G7 | 「drift < 20%」缺度量机制 | 降级为「CI 上报/定性」，与「不做 Dashboard」对齐 |
| G8 | 冲突优先级表述与 Cursor 不符 | 纠正：多来源规则并存注入，冲突靠**作用域/命名规避**，无硬覆盖 |

## 2-3. 逐能力可行性（要点）
- `install`/`update` ✅：copy 默认正确；必须补 clean sync + manifest。
- `check` ✅：主实现用 `git ls-remote --tags`（零额外依赖、跨 GitHub/GitLab/自建）；**内置纯 bash semver 比较**，避免依赖 GNU `sort -V`。
- 升级提醒 V-04 ⚠️（最脆弱）：**三层降级** = ①`additional_context` 注入 ②stderr/marker 文件兜底 ③CI 退出码（覆盖云端）；并缓存降噪。
- `init` ⚠️：零依赖下不覆盖既有 hooks.json，改手动合并提示。
- 版本 pin V-02/V-03 ✅：经 `git archive <ref>` 导出到临时目录，不改动源工作树。

## 2-4. 关键补充建议（P0）
- CLI 自举（`install.sh`）、tag 为版本真源 + CI 断言、clean sync、integrity manifest、供应链缓解（签名 tag / CODEOWNERS / 分支保护 / 生产 `--commit` pin）。
- 可测试性：`shellcheck` + 冒烟测试 + CI 矩阵（ubuntu/macos）；脚本 `set -euo pipefail`。
- 可移植性：避免 GNU-only（`sort -V`/`readlink -f`/`sed -i` 差异）。

### lock schema 增补（已落地）
```json
{
  "source": "https://github.com/<org>/cursor-standards",
  "version": "1.2.0", "commit": "abc123", "installedAt": "…Z",
  "installMode": "copy", "cliVersion": "0.1.0", "dirty": false,
  "manifest": { "rules/standards/std-general.mdc": "sha256:…" }
}
```
> 注意：`source` 写入前会**剥离 URL 中的凭据/token**，避免 lock 泄露 secret。

## 2-5. 更优方案
- **混合分发：全局基线 + 项目 pin**。`--global` 装到 `~/.cursor/`（一次装、跨项目生效，解决换机）；需锁版本的仓库再项目级 `install`。
- **复用 skills.sh 生态**：`cursor-std` 专注 rules+skills 的统一治理，skills 目录遵循开放标准即可被 `npx skills` 互操作（详见附录 A）。
- **与企业版 Team Rules 并行**：本方案定位「不依赖企业版的通用方案」。

## 2-6. 技术路线修订
- Phase 1（MVP）前移：`git ls-remote` 版本检查、clean sync、manifest、`--version` pin、升级提醒三层降级。
- Phase 2：供应链保护、CI 示例（warn-only / fail 两种）。
- Phase 3：Go 二进制、submodule 强 pin、私有 API（若不用 `git ls-remote` 兜底再考虑）。

## 2-7. 风险表

| 风险 | 影响 | 对策 |
|------|------|------|
| hook 供应链：中央仓库被改即在所有机器 session start 执行代码 | 高 | 签名 tag + CODEOWNERS + 分支保护；hook 极简只读；选装 + 显式启用；生产 `--commit` pin |
| `sessionStart` 注入丢失 / 云端不触发 | 升级提醒失效 | 三层降级（文件+stderr+CI 退出码） |
| GNU-only 命令在 macOS/Git Bash 差异 | 部分环境失败 | 纯 bash semver、封装 compat、CI 矩阵 |
| clean sync 误删同级 `local.mdc` | 破坏本地规则 | 严格只接管 `standards/` 子目录 + 测试覆盖 |
| VERSION 与 tag drift | check 不可信 | tag 真源 + 发版 CI 断言 |

# 第三部分：设计决策记录（已定案）

| 问题 | 决定 | 说明与落地 |
|------|------|-----------|
| **Q1 Skills 目录** | **A：`.cursor/skills/`** | 面向 Cursor，最直观；未采用 `.agents/skills/` 开放标准 |
| **Q2 托管地址** | **当前仓库，个人场景优先** | `source` 取 origin 并剥离凭据；`git ls-remote` 覆盖私有场景，无额外 token 逻辑 |

| **Q5 `diff` 命令** | **B：不实现** | 升级前自行看 CHANGELOG |
| **Q6 `remove` 命令** | **需要 → 已实现** | 删受管子目录 + lock，保留 `local.mdc`/hooks |
| **Q7 规则命名前缀** | **B：加 `std-` 前缀** | `std-general` / `std-git-workflow` / `std-python` / `std-typescript`，避免 `@` 引用歧义 |
| **Q8 发版断言** | **A：GitHub Actions** | `release-check.yml`（`VERSION==tag`）+ `ci.yml`（ubuntu/macos smoke） |
| **Q9 Phase 3** | 未排期 | Go 二进制 / npm 封装 / 发布 skills.sh / submodule 暂不实现 |

| NF-05 安全 | ✅ | clone + 本地 install；无 curl\|bash；lock 剥离凭据 |

## 超出原需求的增强（➕）

- **integrity manifest + `verify`**：sha256 校验受管文件，检测手改/缺失/多余（退出码 4）。
- **clean sync**：传播上游删除且不碰 `local.mdc`。
- **纯 bash semver 比较**：不依赖 GNU `sort -V`，提升可移植性。
- **CI**：`ci.yml`（ubuntu/macos 冒烟）+ `release-check.yml`（VERSION==tag）。

# 附录 A：能否用 `npx skills` 承载定制化的 skills / rules 分发？

结论先行：

| 目标 | 能否用 `npx skills` 实现 | 说明 |
|------|--------------------------|------|
| **Skills 分发/更新** | ✅ 基本可以（有取舍） | `npx skills` 就是 skills 的包管理器 |
| **Rules（`.mdc`）分发** | ❌ 不能 | 该 CLI 只管 `SKILL.md`，不碰 `.cursor/rules/*.mdc` |
| **semver / tag / commit pin** | ❌ 原生不支持 | 无 `@version`/`@commit` git-ref pin；`update` 拉分支 HEAD |
| **零运行时依赖（NF-01）** | ❌ 冲突 | 需 Node/npx |

因此它**不能作为「rules + skills 统一、可版本追溯」的单一分发底座**，但可作为 skills 的**可选安装器 / 互操作层**。

## A.1 `npx skills` 能做什么
Vercel Labs 开源 CLI（配套 [skills.sh](https://skills.sh/) 与 [agentskills.io](https://agentskills.io/)）：
- 来源灵活：`owner/repo`、完整 URL、`owner/repo@skill`、子目录、任意 git URL、本地路径；私有仓库靠 `GITHUB_TOKEN`。
- 命令：`add` / `find` / `list` / `check` / `update` / `remove` / `init` / `use` / `experimental_install`。
- 作用域：`-g` 全局 `~/.cursor/skills/`；项目级 `.agents/skills/`。
- 更新：比对本地 skill 文件夹 hash 与 GitHub **默认分支** 版本；仅追踪 `-g` 全局安装。

## A.2 关键差距
- **rules 管不了**——而团队核心规范（`alwaysApply:true`）恰是 rules。
- **无真正版本 pin / tag 语义**——它「跟随分支 HEAD 滚动更新」，与本方案「按 tag 可追溯/可 pin」相悖。
- `alwaysApply:true` / 带 `globs` 的 rule **不适合转成 skill**（Cursor 2.4+ 的 `/migrate-to-skills` 也明确拒绝迁移这两类）。

## A.3 推荐：混合 / 互操作，而非替换
- **Rules**：始终由 `cursor-std`（copy + lock + clean sync + manifest）治理。
- **Skills**：由 `cursor-std` 一并 copy 并纳入同一 lock，实现「rules 与 skills 同版本/同 tag/同 pin」的统一治理；目录若遵循开放标准，个人仍可用 `npx skills add <仓库>` 临时安装（生态兼容白送）。
- 把 `npx skills` 当作「面向个人的可选安装/发现入口」，而非团队规范的分发底座。

> 本项目按决策 Q1=A 使用 `.cursor/skills/`（面向 Cursor）；如后续需要与 skills.sh 生态深度互操作，可评估切换到 `.agents/skills/` 开放标准目录。
